KinSealStudio 5.1 复刻可行性分析

分析日期：2026年11月7日（北京时间）｜目标：标准版 2026-08-25 安装包及用户提供的 Installed 目录｜证据类型：文件解析、交付帮助文档、REA 与 Ghidra 静态反编译

结论：具备实质性的复刻条件，建议立项做“独立编辑器 + 单型号兼容验证”。

画面编辑、常用控件、PLC地址配置、报警/曲线/配方等功能，可以根据交付文档和实际数据重新实现。旧工程双向兼容已有格式入口；兼容原触摸屏需要继续恢复编译 DAT 格式、屏端 ABI 和下载协议。现有证据尚不能支持“全部型号、全部控件和原硬件完整兼容”，也不能将反编译结果当成原始源码。

3 技术架构及其对复刻的影响

主机编辑器是原生 C++ / Qt 4.6.3 / MinGW 路线。 依据是 PE 导入表、GCC C++ 修饰名、mingwm10.dll、libgcc_s_dw2-1.dll，以及 QtCore4.dll 内的 4.6.3 与构建前缀。还实际使用 QScintilla、Qt XML/SQL/Network/SVG、QuaZip、MiniLZO 和 QDataStream。界面、属性对话框、对象序列化、像素生成和编译逻辑可能分布在同一个大 EXE，不能把 DLL 边界当成完整业务边界。

现有组件有可分析的原生机器码。 已用 Ghidra 12.1.4 对 USB 包装函数、Modbus 驱动入口做出有效伪代码。主程序也保留 Qt 信号/槽和诊断字符串，例如 SaveProjectToFile(QString,int)、MainWindow::SaveProjectToData b、StartCompileThread()，可作为下一步追踪入口。上述证据不等于已经恢复全部保存、编译或加密算法。

4 工程和编译格式已经确认了什么

4.1 三类后缀需要分别处理

对象证据强度结论与边界
.hs中文帮助正文文档称其为可编辑工程。尚未收集一组真实的 .hs 工程并验证完整读取/写回。
.knr帮助正文 + 现有 upLoad.knr 实物文档称可把 .hs 压缩为 .knr 以跨电脑迁移。compile/upLoad.knr 实物是“4字节大端解压长度 + zlib”的结构。不能由一个上传样本推及所有历史、带密码或迁移文件。
.knscompile/load.kns 实际归档解析该样本是普通 ZIP / Deflate，19 个成员未设加密位；全部成员均成功解压，并与 compile 下同名文件逐字节一致。它是编译/部署相关产物，不应当成编辑工程格式。

4.2 QDataStream 有可复核的结构证据

compile/upLoad.knr 的前4字节为大端长度 0x0015F16B，即 1,438,059；随后是以 78 DA 开始的 zlib 数据。实际解压长度与声明完全一致。解压后偏移0出现大端长度40，后接 UTF-16BE 的 KinSealStudio-V1.0.2；随后有整数122、型号、PLC配置和 PNG 资源等。与 Qt 的 qCompress + QDataStream 行为高度吻合。[S3]

根目录 tempFile 也能解析相同的字符串头。更重要的是，其中一个 PNG 的长度、800×480 RGB8 IHDR、144个chunk、IDAT解压长度和 IEND 边界已完整核对：PNG占文件约99.73%，其余元数据只有3,169字节。这是有效的格式起点，却不是复杂工程的充分样本。[S4]

Qt 流默认使用大端，但应用可以混用自定义结构、原始字节块、不同精度和版本分支。工程头中的122目前只能视为版本相关候选字段。不能把看见的 QString 串直接连接成“完整格式定义”，也不能用当前无密码样本推断所有保护工程都没有加密。

4.3 编译 ZIP 已拆到真实数据层

load.kns 包含 AMZ101W01.bin、HZ.bin、Modbus_RTU_com1.bin、load.bin、Usbload.bin、upLoad.knr，以及 SysPara.dat、AddrPara.dat、ControlPara.dat、ControlPixel.dat、SheetPara.dat、SheetPixel.dat、报警、采集、曲线、图片索引等数据。已确认19项的名称、偏移、压缩方式、长度、SHA256和目录文件一致性。[S5]

真正的兼容难点已经缩小到 DAT 的语义。 要恢复控件类型编号、记录尺寸、页/控件索引、地址编码、字节序、图像色彩格式、对齐/保留字段、资源偏移、长度和校验。ZIP本身容易重建，生成“结构有效但行为错误”的参数表才是主要风险。

当前 language.ini、tempFile 与编译残留中出现不同的型号字段，编译归档还携带 AMZ101W01 固件；这些材料不能被当成同一次操作的一致运行快照。必须通过字段解析和差分工程确定具体含义。

5 型号配置和 PLC 驱动的证据

5.1 型号能力是明文 XML

model.dat 和 modelInfo.dat 都是带 BOM 的 UTF-8 XML。前者81个条目、80个唯一型号，重复项为 AMT070W016-L1024X600R；后者80条，与唯一型号集合匹配。字段明确给出分辨率、设备ID、传输缓冲、画面/控件配额、固件、字库、宏库、运行入口、LB/LW/RWI地址、驱动目录和仿真程序。[S6]

例如 AMZ070W01 定义为800×480，并引用 script_amzlib.a、Link/serial_amz/、V51_800x480.exe 和 onlineV51_800x480.exe。这些配置可直接用来建立新的设备描述层，不必先逆向一个“加密型号数据库”。

配置数量不能等同于实物支持数量。 对80个型号进行安装树文件名交叉检查，脚本库、GUI库、字库和两类仿真程序均能找到引用文件，但8个型号引用的底层固件缺少同名文件，另有2条启动图像引用未找到同名外部文件。启动图可能内嵌于 Qt 资源；固件也可能存在回退/别名机制，均未验证。[S7]

缺少同名固件的型号：AMT035W124-L320X480C、AMT035W124-L320X480R、AMT050W016-L480X854R、AMT080W124-L800X600C、AMT080W124-L800X600R、AMT150W016-L1024X768C、AMZ035W06、AMZ043HW04。

5.2 Windows 与屏端协议插件属于两套机器码

PlcDll 的51个DLL全部是 x86 原生 PE，每个仅有一个命名导出 DllFun。Link/serial_amz 则有63对 COM1/COM2 裸 ARM 驱动；两端口版本均不完全相同，Modbus RTU 两个版本仅差19字节。这支持“共同协议逻辑 + 端口/宿主接口差异”的推断，尚不构成完整 ABI 说明。[S8]

Modbus Windows DLL 的 DllFun 导出跳到 0x100123c0。反编译确认它保存传入函数指针，用7个全局地址调用该指针，再调用内部初始化函数。这证明存在宿主回调/共享数据契约；7个地址的完整类型、读写方向和生命周期仍未恢复。REA证据 ev_f291ea1c3142b960636895ff3a75322230b84a9e1c851e312f86248ccfd6bd8d。[R3]

Link下许多扩展名为.ini的文件实际上也是 XML，提供串口参数、寄存器类型、地址范围和进制。例如 Fx3U 的 X/Y 八进制与串口配置已有明确数据依据。实现时仍需确认位/字/双字映射、站号、读写命令、错误应答和时序，不能仅加载清单就称为协议兼容。

若需要复用旧 DLL，64位新程序不能直接加载32位 DLL。 可将其放在独立 x86 桥接进程，通过 IPC 连接新编辑器；屏端 ARM 驱动仍需另行处理。Windows 的 DllFun 入口不能直接作为屏端驱动实现。

6 USB 下载和仿真的可复刻边界

6.1 USB 传输层已经得到反编译证据

AMZUsb.dll!AmzUsb_connect 使用 usb_init / usb_find_busses / usb_find_devices，打开设备后调用 usb_claim_interface(handle, 0)，设备日志常量为 VID 0x7365 / PID 0x616C。驱动INF也包含这一ID。REA证据 ev_4f56ffb112d2f4a8d44371119bb6199c0ad0ac9892ef33daf5cf76ae1305aaf0。[R1]

AmzUsb_writeRaw 通过 usb_bulk_write(handle, 1, buffer, remaining, 5000) 进行写入，循环处理部分写入。即已确认 OUT端点参数1、每次调用超时5000毫秒及基本返回行为。REA证据 ev_7c8d1ef75ecf2439e688bd46f198a5b973ac9d8976265caca1e3cb7be93848c1。[R2]

“能发 USB 字节”与“能下载运行工程”之间仍有应用协议。 尚未确认下载会话握手、设备/型号识别、包头、命令号、分包序号、CRC/校验、确认/重试、写入目标和完成激活流程。本次没有抓取通信，也没有向设备写入数据。

6.2 仿真器是很有价值的验证基准

离线和在线目录各有8个分辨率程序。二者包含 uC/OS-II WIN32 / uC/GUI 相关字符串；在线版实际额外导入串口 API、LoadLibraryA、GetProcAddress 并包含 PlcDll 路径。800×480在线版中有明确的 compile 数据路径，如 ControlPara.dat 位于文件偏移1,689,532，SheetPara.dat 位于1,689,432。[S9]

这使“新工具生成 DAT → 官方仿真器验证显示与读写”成为有希望的中间关口。但路径字符串不等于已经观察到真实加载流程，仍需在隔离副本中确定工作目录、启动参数和共享内存契约，再做后台运行测试。

帮助声明离线模拟不支持宏，在线模拟30分钟后退出。这是规格线索，不作为本次实测结论，也不能用离线模拟成功替代宏或原屏测试。[S10]

7 宏指令与屏端固件是独立的高成本部分

宏帮助声明支持 ANSI C89、初始化/全局/画面/按钮等宏。实际交付 ARM Developer Suite 1.2 工具、头文件、标准 ar 静态库及 ELF 目标文件。已解析 script_amzlib.a 等库的导出索引，存在 PUTCHARS、GETCHARS、ScreenOpen、CRC、LB/LW/RWI 和绘图相关接口。[S11]

当前型号配置把宏库和固定入口/地址明确关联起来，例如 macroEntry=80520400、macroRWEntry=80440000 及 macroLB=0x804c5010。因此语法能编译只是第一步，还需要调用约定、链接地址、重定位、运行时支持、变量宽度和共享内存布局保持一致。不能默认换成 GCC、Clang 或 WebAssembly 就能在原固件上执行。

Firmware的87个BIN中，84个带 ARM 分支与 eGON.EXE / EXEC 头，另3个是HZ字库。样本还含 uC/OS-II Idle、uC/GUI诊断及 suniii USB驱动路径。这支持 ARM + RTOS/嵌入式GUI的判断；具体SoC、RAM映射和启动链仍不能仅由字符串确定。随附TurboWriter是旧W55FA91/93/95工具，不能据此把当前AMZ设备认定为Nuvoton。[S12]

如果目标是沿用原屏，优先恢复数据与ABI；如果目标是自研屏，可设计新的运行时和脚本引擎，但这会改变“原屏兼容”的项目目标。原厂固件、GUI库、编译器或驱动的技术复用还会形成持续依赖，交付分发时需核对其许可。

9 推荐的实现路径与验收关口

建议采用 Qt 6 / C++ 建立独立画布、属性系统、撤销重做和统一项目模型。原格式读取器、原格式写入器、编译后端、PLC通信和部署器分别实现。自有项目格式应包含明确版本；原格式作为导入/导出适配层。复用32位组件时以独立x86进程隔离其ABI，不把整个新编辑器锁在Qt4。

最有价值的第一个验证：让新工具生成的一个按钮和一个数值显示控件，被官方仿真器识别，并能读写Modbus；随后用一个实际型号验证原屏。这个关口能同时检验控件记录、地址、渲染数据和运行链路，比先实现大量外观界面更能校准可行性。
