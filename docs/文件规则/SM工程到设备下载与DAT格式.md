# KinSealStudio V5.1 从 SM 工程到设备下载

核对日期 2026-11-22。依据项目源码、已归档的原厂编译件和 Lite 实物下载回执，以及两款固件的分析记录。

## 结论

**已跑通限定机型和工程范围的下载链，完整原厂编译器及全部 DAT 格式仍未掌握。** 已验证的独立编译和 USB 主线面向 `AMT070W124-L800X480R` 的 800×480 普通单页工程。静态、含动态控件、再含普通宏的 10／12／14 个数据段均有真实下载回执和局部实屏结果。可生成的控件、样式、宏和 PLC 组合以当前编译预检为准。更广的 SM 源结构和设备装载研究仍需逐项接入编译器并验收。[编译边界](../../design_plan/A05_源格式与设备编译契约.md) · [实屏回执](../stage10-evidence/physical-field-20261119/field-summary.json)

## 2. 当前已实现的编译流程

1. **读源并验证工程。** 已核 V5.1 SM 头依次为 Qt QString `KinSealStudio-V1.0.2`、大端 u32 版本 `122`、型号 QString。已核 QString 使用大端字节长度和 UTF-16BE。结构读取按类型、语言、资源、配置、页面和引用的实际分支遍历。编译入口通过 `HmiProject::load` 将支持的 `.sm` 或 `.ksp` 读入模型，可直接接收支持范围内的 `.sm`。原件归档、结构读取、语义导入各有自己的成功条件。[SM 详细文法](SM源工程格式规范.md) · [源加载入口](../../src/project_model.cpp)

2. **做设备预检。** 当前设备后端要求目标 AMT、800×480、一个普通启动页、1～100 个对象、1～8 种语言，并检查几何、控件类型、活动配置、资源、宏索引和地址连接。未恢复的多页或活动字段会阻止整包生成。原厂源中已有的类型或字段，还要经过独立的设备编译门槛。[编译预检](../../src/device_compile_plan.cpp) · [能力入口](../../src/project_capabilities.cpp)

3. **生成页面图、控件记录和扫描表。** 单语言、无显现条件的静态文本和受限的静态图形可烘焙到页面背景。位按钮、字按钮、指示灯、功能按钮，以及多语言或带显现条件的静态文本，按当前支持的属性写控制记录和状态图。状态图按控件、语言和对应状态顺序组织。扫描表收集实际需要读取的地址，纯写入和通知有各自的语义。[编译入口与各段生成](../../src/independent_downloader.cpp) · [图帧顺序及索引规则](../../design_plan/A05_源格式与设备编译契约.md)

4. **补充宏和原始工程快照。** 支持的普通宏用真实 ARM SDK 执行 `armcc → armlink → fromelf`，把 RAW 代码和索引写入 `MarcoRun.dat`，同时生成匹配的 `MarcoVar.dat`。`upLoad.knr` 使用 qCompress，文件内是四字节大端解压长度和 zlib 数据。按解包结果识别原厂 SM 或 Lite JSON；现有 Lite 通用编译路径生成 JSON，一些已验证的单文本兼容路径保留原厂 SM。[宏打包](../阶段8宏编辑编译与验收.md) · [KNR 检查与提取](../../tools/stage6_media_bundle.py)

5. **导出并复核设备包。** 每个段记录原始长度及 SHA-256，最后写 `compiler-manifest.json`。包校验重读文件，核对型号、段集、记录数、图块长度、LZO 解压长度、帧偏移及计数。文件和线上段各自记录哈希。用新目录留存同一批产物，离线状态以编译清单和包校验回执核对。[设备包验证器](../../src/device_package.cpp) · [离线清单与验证](../../src/main.cpp)

6. **生成线序并与实物验收。** AMT 按识别、开始、各段及状态确认、提交、重启和后续读收尾执行。`upLoad.knr` 还需在线上段外加四字节大端的压缩文件长度；这与文件内部的解压长度是两个字段。默认 COM1 驱动的长度放在命令的小端参数区。传输结果记录提交确认和重启收尾。文字、触摸动作、宏、PLC 和运行值保持分别由实物观察确认。[线序与封装](../../src/device_transfer_plan.cpp) · [传输和验收](../阶段6传输与介质实现及验收.md)

| Lite 工程类型 | 实际数据段数 | 段步骤数 | 归档观察 |
| --- | ---: | ---: | --- |
| 静态单页 | 10 | 12 | 上移标识的补测页同时看到标识和 4×4 表格 |
| 含动态控制记录 | 12 | 14 | 标识、表格和上方控件可见；独立样例另有字按钮、语言按钮和按压观察 |
| 动态控件及普通宏 | 14 | 16 | 复位后触发宏，独立 LB10 指示从 0 变到 1 |

每种计划含两个只有命令与状态检查的步骤。以上三类已有提交与重启收尾回执。采用 Windows Qt 字体后端复验过实屏文字，曾有 USB 全部确认而文字呈方框的离屏字体差分。[实物原始记录和字体对照](../../design_plan/阶段10现场续验_20261119.md)

## 3. Lite USB 路径的 12 种 DAT 格式

下表的偏移从文件或记录第 0 字节起算。LE/BE 分别为小端/大端。长度和布局限于当前已核定的机型、样本及分支。

| 编译文件 | 当前已掌握 | 仍待验证 |
| --- | --- | --- |
| `SysPara.dat` | 系统参数。AMT 已验证的起始模板为 4,998 B，通用编译路径将启动语言索引、语言数量写入 2172、2174 的 LE u16。原厂样本另有屏保、闪烁、初始权限、触摸声音的稳定差分 | 系统参数完整布局、范围和运行消费者，未知区域及活动配置独立生成 |
| `SheetPara.dat` | 页面表。已用 72 B 单页记录，`+0x02` 单字节是控件数、`+0x03` 是独立标志，`+0x44` 是 LE u32 控件图解压总量。AMZ 装载研究还核对了样本的宽、高字段 | 其他页面标志、多页／窗口／键盘／Logo 的索引和场景间引用 |
| `SheetPixel.dat` | 页面背景。已知单张 800×480 RGB565 紧排图原长 768,000 B，作为独立 LZO1X 压缩流；可独立生成并回解 | 其他机型和多页组合、非默认解码方式、全部字体与图形样式一致性 |
| `ControlPara.dat` | 当前每条 640 B。已生成 type10 的 0/1/3/4 子型，以及动态静态文本 type28。已核公共几何、解压像素偏移和原长、地址槽及各子型的部分活动字段 | 原厂其他类型、私有字段、未赋义区域、复杂组合和实际运行全矩阵；已找到部分类型及装载入口 |
| `ControlPixel.dat` | 当前状态图逐帧 RGB565 行紧排、独立 LZO1X、以 32 B 对齐补零。已实现相应控件的语言、状态和额外闪烁帧顺序 | 特殊控件帧结构、动态遮挡、非默认图像编码及全部语言和状态分支 |
| `PicLenPara.dat` | 头部 2,400 B，为三个 200 项 LE u32 页数组，分别索引背景压缩长、控件图压缩总长、控制图数量。后续每帧 12 B，已核编码槽、补齐长、有效压缩长 | 实际多页排列及其他编码标志；AMZ 所测解码器读记录首字节选择分支，编码槽其余字节的通用含义仍待核 |
| `AddrPara.dat` | 200 B 每页扫描项数表，随后为每项 12 B。数量在 `+4`（LE u16），起址在 `+8`（LE u32）。当前离线编译已核默认 Modbus RTU COM1、站号 1、节点 1 的读取扫描 | 真实 PLC 联动、其他驱动、非默认连接、多页、内部分类标志和全地址范围 |
| `AlarmPara.dat` | 当前使用已验证的 47,840 B 默认模板。已有原厂差分与固件装载线索 | 活动报警、地址、文本和索引的完整格式，配套语言、确认、历史和恢复逻辑 |
| `Collect.dat` | 当前使用 1,424 B 默认模板。AMT 固件导入和装载使用相同块选择值 `0x41`，从 `+0x02` 读项数，以 40 B 步长取各项类型，并重算运行区 `+0x01`。三份非空原厂样本已核对 | 采集触发、周期、记录的其他字段、历史存储及活动采集的独立生成 |
| `Curve.dat` | 当前使用 501 B 默认模板。AMT 固件从首字节读描述符数量，从 `+0x01` 按 52 B 步长装载，各描述符 `+0x06` 的类型和三份原厂趋势或 X-Y 样本相符 | 描述符内通道、点位、采样和显示字段的完整映射，多描述符原厂编译规则 |
| `MarcoRun.dat` | 可生成普通宏容器。已核 1,024 B 头，其中有宏数、标志和 LE u16 RAW 长度数组，头后串接 RAW。实屏已验证一个普通宏案例 | 原厂活动宏排序、禁用过滤、启动／全局／画面调度以及设备运行组合 |
| `MarcoVar.dat` | 当前为每宏 904 B 全零块，覆盖零地址变量这一分支。原厂已观测到更丰富的变量槽，AMZ 有变量组读取点 | 有变量时的字段映射、不同地址族、读前同步、写后提交及变量交叠和调度 |

关键交叉校验举例。一个 100×50 的控件每帧应解压为 `100 × 50 × 2 = 10,000` B。`ControlPara.dat` 的 `+0x0C` 指向解压后的像素位置，`+0x10` 记录该控件全部活动帧的原长。`PicLenPara.dat` 使用实际压缩长度与补齐长度定位压缩块。页级控制数和原始像素总量再与 `SheetPara.dat` 核对。一个尺寸变动可能需要同步改上述三种索引与控制数据以及像素本体。[字段偏移和图像不变量](../../design_plan/A05_源格式与设备编译契约.md) · [校验实现](../../src/device_package.cpp)

## 5. AMZ070W01R 能复用到哪里

原厂工程型号键为 `AMZ070W01`。安装包已取得带该型号的 SM 快照，其头可以识别，当前 Lite 的主体解析和 USB 整包路径仍未开放该目标。已有 AMZ 固件研究执行了实际 ARM 例程，对一份 AMT 编译工程的页面表、12 条控件和 46 个压缩图帧做了离线互证，LZO 解码结果与独立解码器一致。这为共用部分页面、图像、索引和控制记录提供了直接证据。该例还观察到 AMZ 的 JPEG 分支，图像头解析已有离线验证，硬件解码后的像素待实屏验证。[SM 机型缺口](SM源工程待解析清单.md#sm-open-project) · [AMZ 装载和解码验证](../../firmware_analysis/amz070w01-disasm-20261119/AMZ070W01固件工程解析与PLC通信总报告/AMZ070W01固件工程解析与PLC通信总报告.md#render)

正式支持 AMZ 仍需要同机型的原厂最小工程、分段编译件及实物握手与下载回执。先验证静态画面，再验证位按钮与独立指示，随后按所需功能验证 PLC、宏、多页和其他下载方式。完整芯片烧录另有镜像布局、写入方式和启动验证要求。

## 6. AMT070 固件与编译产物交叉验证

2026-11-22 用脚本将指定反汇编清单的每行原始字节与 907,264 B 的 AMT070 原厂固件逐段比对。固件 SHA-256 为 `74d510f150dc8edadf8e967bdb3c00ca5790ca68b9da6f906125a5234a485c24`。锁定关键 ARM 指令原字后，从指令位域得到读取偏移、步长和常量，再对真实原厂编译件重算。文件名路径的关联来自清单的 `PARAM` 注释，路径字符串另从固件原始字节核对。脚本执行的是选定指令规则的静态重算，实物结论沿用已有回执。[验证脚本](../../tools/verify_amt070_compiled_firmware.py) · [机器证据](样例/AMT070编译段与固件互证.json) · [AMT070 反汇编](../../firmware_analysis/amt070-disasm-20261119/full_disassembly.asm)
