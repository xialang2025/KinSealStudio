# AMZ070W01 应用固件读取的离线界面描述符

原厂 V5.1 写出 1,704 字节的 `Usbload.bin`。AMZ070W01 应用固件在介质工程加载函数 `0x8004EA48` 中，把已读取文件的前 904 字节复制到 `0x80348790`。本轮从 ARM 指令核对了该工作区 11 个直接引用点，并复验 Git 原厂包 441 份、已安装 AMZ070W01 一份及安装器内六页 AMZ101W01 一份。固件读取路径仅对这份 AMZ070W01 固件成立。[反汇编及型号说明](../../firmware_analysis/amz070w01-disasm-20261119/反汇编说明.md) · [逐包 SHA、时钟和复验结果](样例/AMZ离线描述符固件读字段与同进程整件复验_20261128.json)

## 原厂应用固件用到了哪些字节

偏移从文件首字节计数。数值除特别说明均为小端。ARM 读地址由常量池中的工作区基址加指令位移得到。`0x8004EAD8` 设置复制量 `0x388`，`0x8004EAE8` 调用复制函数。因此从 `+0x388` 开始的上位机普通页像素长度表不在这次 ARM 复制的前缀内。

| 文件位置 | 固件内的读法 | 原厂 UI 编译字段 |
| --- | --- | --- |
| `000` | `0x80096F64` 取一字节，等于零时提前返回 | 启动画面类型 |
| `002`、`04C…055` | `0x80081724` 取标志，`0x8008172C…173C` 从选项区固定复制 10 字节 | 原厂下载设置组合位与选项文本 |
| `004…007` | `0x80098A14` 取一个字，后续按高字节在前写入内部记录 | 从本地编译整秒产生的 qrand 标识 |
| `00C…00F` | `0x8008FBA0` 比较版本字 | 此版编译器写 123 |
| `014…017` | `0x80097578`、`0x80097724` 读取宏数量并在零值时提前返回 | 工程宏数 |
| `01C`、`130`、`162` | `0x80096814` 仅读取端口计数字段的低字节，`0x8009684C` 与 `0x80096980` 以第一个零为止拼接两项驱动文件名 | 通信端口数、前两个 50 字节驱动名槽 |
| `0F8…0FF` | `0x80097C58`、`0x80098300` 取实际字节数，后续按剩余长度分块 | 背景像素及控件像素文件长度（允许空控件图） |

机器核验重新枚举了反汇编中地址落在这段 904 字节内的已解码直接数据字面量，并核对它们的指令引用及上述读宽。这里还没有对间接调用、通过其他工作区转移的数据或其他固件版本给出完整覆盖保证。[原始指令清单](../../firmware_analysis/amz070w01-disasm-20261119/full_disassembly.asm) · [离线核验程序](../../tests/verify_amz_usb_media_descriptor.py)

## 从其他编译文件预测时钟

原厂 V5.1 的 `0x006422DB` 调用 `0x00635ABC` 写 `load.bin`，随后 `0x0064232A` 调用 `0x00641168` 写 `Usbload.bin`。这确定了两个文件的写入顺序。对每个历史包，读取当次 `SysPara.dat` 从 324 起的七个 32 位本地时间字段，以及前一个文件 `load.bin` 自己的 ZIP DOS 修改时间。先取两者的较晚时间，用距午夜整秒 `s` 算出 `((214013 × s + 2531011) >> 16) & 32767`，再与原厂字段比对。预测不读取目标描述符及其时间戳。

443 份对照中，直接使用系统段时钟有 348 份的四字节相同，结合前一文件时间后为 **400 份**。另 43 份的随机字对应紧接着的下一秒。预先用这两秒分别生成候选，在 443/443 份中都包含原值。按两个候选的相同部分看，438 份的高三个字节确定，另 5 份的高两个字节确定。该两秒范围是这批历史编译的观测结果，供比较使用，不作为其他机器编译耗时的上界。DOS 时间以两秒为单位，两次编译步骤也可能跨秒。提供原厂当次准确的调用秒数仍比估算更直接。[原厂字段写入规则](Usbload有效字段与同源差分_20261128.md)

## 整个描述符和 KNS 的结果

| 独立输入及比较口径 | 样本 | 结果 |
| --- | ---: | --- |
| 用当前 `load.bin`、已编 UI 散件长度、上节独立时钟估计值，原厂未确定的区域采用零 | 443 包 | 所有已定位的直接读取结果中，除时钟外逐项相同（按文件名长度，每包检查 44 或 54 字节，含时钟）。400 包连时钟也相同。完整 1,704 字节相同为 **0/443** |
| 按日志先选定同进程相邻两次编译。沿用**上一次**原厂描述符中的未确定区域，根据当前工程元数据、长度和独立估计秒数重写已知字段，再取本次原件比较 | 8 份日志共 29 对，其中 27 对有前后原件 | **14/27** 份完整 1,704 字节相同，其中 10 对的输入 SM 确实发生改变。其余 13 对相差 1 至 9 个字节，全部限于时钟及短驱动名终止符后的十字节 |
| 将上一步生成的描述符与本次原厂的其他介质成员、各成员原日期一起重新压缩，用完整文件比较目标 KNS | 上述 27 对 | **14/27** 份完整 KNS 相同，与整描述符的 14 对对应 |

前后运行按原始日志的 PID 和顺序选取，用归档 SHA-256 绑定已存原件，重复报告的同一有序对只计一次。两个缺原件的相邻对在回执列明。未用目标段修补结果，也没有以旧进程作为所有新工程的通用默认初始状态。短驱动名反例出现在源码能产生而原厂仍有多种取值的区域。原厂主机 `0x00641554…0064158B` 对活动槽最少复制 20 字节；当名字为九字节的 `_com1.bin`，名称和零终止符共占十字节，此后的十字节可能变化。前述 ARM 字符串用法只读取至第一个零。这个行为也解释了整件差异为什么不能仅靠修改驱动名解决。

## 复跑与磁盘样件

从项目目录执行。下面第一个命令从 Git 原件和额外包重新复核。第二个命令要求提供实际历史编译秒数。第三个命令演示从同一会话的较早描述符和独立时间生成对照样件。样件路径必须是新的 `.bin` 文件。工具保持原输入和已有输出，普通 JSON 路径会将估算时间单独列出。

```powershell
py -3 -B tests/verify_amz_usb_media_descriptor.py --revision e3b72657 --report 本次离线核验.json 原厂七寸.kns 原厂六页.kns
py -3 -B tools/rebuild_usb_metadata_fields.py 当前编译散件 --seconds 36000 --comparison-bin 比较样件.bin
py -3 -B tools/rebuild_usb_metadata_fields.py 当前编译散件 --preceding-load-time 2026-11-14T10:00:00 --prior-descriptor 较早工程/Usbload.bin --comparison-bin 会话比较样件.bin
```

对照入口只在磁盘生成样件。本轮未向触摸屏发送文件，默认产品入口没有启用未确定的介质字节。用户手动复验的条件继续在总清单记录。[字段编码和受控输出工具](../../tools/rebuild_usb_metadata_fields.py)
