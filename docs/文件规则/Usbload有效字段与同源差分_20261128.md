# Usbload.bin 有效字段重建与同源对照

原厂文件长 1,704 字节。本次用原厂 V5.1 可执行文件的写入函数确定有效字段，再用 441 份 Git 归档、安装目录的 AMZ070W01 和安装器的六页 AMZ101W01 逐字节比对。三类样本分别能重建 426、436、456 字节。差异判定包括字符串截断、结尾、已确定的填充和四字节整数的全部字节。

## 输入和输出

工具从先前已能独立生成的 `load.bin` 读取 V122 Qt 4.8 流，另取四个编译散件的字节长度。可传原厂调用 qrand 时的本地午夜起整秒。缺少此值时，工具只输出与工程和散件有关的字节。工具生成的 JSON 仅列出已核实的偏移区间，其余区间省略。

```powershell
py -3 tools/rebuild_usb_metadata_fields.py "工程/compile" --load-metadata "新生成/load.bin" --seconds 36000 --output "已核实USB字段.json"
```

时间示例 36000 对应当地 10 时整。工程使用简体中文 Windows 默认本地编码时选用 CP936。原厂的 QString 转换依赖编译电脑的本地代码页，工具的 `--encoding` 可以指定实际代码页。对本次项目内的非 ASCII 属性尚缺原厂 USB 介质的独立对照。

## 逐字段规则

偏移从零开始，所有四字节数均为小端。原厂 V5.1 可执行文件 SHA-256 为 `305592b4e4bc1b15a707c7bc832c31f27ca0958b97f9c79a5b50ac6df49e907c`。例中的 f0 至 f3 指同源 load.bin 从前向后的四个布尔字段，顺序可在[介质元数据文法](V122介质load.bin独立生成_20261128.md)查阅。

| 文件位置 | 来源和处理 |
|---|---|
| 0x000 至 0x003 | 依次写启动类型、f2、f1 与（f0 左移一位）的按位或、f3。原厂赋值位于 0x006413FA、0x0064149D、0x006414AE 至 0x006414C2、0x006414D4。 |
| 0x004 | 原厂 Windows Qt 4 以本地午夜起整秒 s 初始化随机数，写入 `((214013*s + 2531011) >> 16) & 32767`。ZIP 时间精度只有两秒，将它用作候选时还要允许文件写入跨秒。 |
| 0x008 至 0x023 | 连续七个小端整数依次为消息控件数、常数 123、普通画面数、工程宏数、面板类型、通信端口数和历史数据配置数。普通画面数取原厂全局画面列表，写端有上限 256，当前源解析的已支持上限为 200。 |
| 0x042 | 10 字节面板型号。先清零再拷贝本地编码，超长截断。实测 AMT070W124-L800X480R 得到十字节 AMT070W124。 |
| 0x04C | 10 字节选项文字，来自 load.bin 的 optionText。 |
| 0x056 | 32 字节编译器签名。已核实的 V122 原件均为 KinSealStudio-V1.0.2。 |
| 0x076 | 128 字节启动图名称，六页原件的非空图名可由同源 SM 重建。以上四段长度的原厂清零和拷贝循环出现在 0x006412FE 至 0x006416CD。 |
| 0x0F8 至 0x107 | 依次是 SheetPixel.dat、ControlPixel.dat、AddrPara.dat、PicLenPara.dat 的文件长度。 |
| 从 0x130 起的四个 50 字节槽 | 每项是当前驱动路径的文件名，空槽为零。短名称的终止符后有部分字节未取得稳定值。工具保留可逐字节核实的名称、终止符、固定零尾和未使用的完整槽。原厂遍历源于 0x00641518 至 0x00641619。 |
| 从 0x388 开始 | 每页一个四字节整数，由 `trunc(宽×高×2)` 得到。六页 AMZ101W01 的六项都等于 1,228,800。 |

## 验证范围

| 原厂样本 | 份数 | 每份可重建字节数（含时间） | 全部所列字节 |
|---|---:|---:|---|
| 单页、短驱动名 | 410 | 426 | 相同 |
| 单页、完整驱动名 | 32 | 436 | 相同 |
| 六页 AMZ101W01 | 1 | 456 | 相同 |

安装目录与六页安装器对照支持从各自的 upLoad.knr 提取原厂 SM，结合三份独立散件先生成 load.bin，再计算 Usbload.bin 的字段。运行时未从原 Usbload.bin 取值；核验调用秒数时，用 ZIP 记录的相邻整秒产生候选，与原件比较。历史调用的确切时间以当时进程实际读取为准。

## 原厂同源双编译能否复现整个文件

Git 基准版本 `e3b72657` 中有 148 组直接保留了相同 input-native.sm 的原始编译目录，共有 272 对。排除四字节时间字段后仍有 266 对文件不同。将分组条件再收紧，要求同一 input-native.sm、同一 load.bin、四个输入散件各自整文件均相同，或两边均缺少相应可选散件，剩下 117 组、241 对。235 对的差异仍存在，只有 6 对在排除时间后完全相同。上述结论只针对这些输入；其他编译散件、工作目录和编译进程的历史状态可能不同。

一个可复验的例子来自 alarm-bar-lifecycle-r1 和 alarm-baseline-r1。对应普通页源 SM 的 Git blob 均为 `ab9596d58834b3945d652f68a84aaa10c54e1c4f`，load.bin 和四个散件也分别完全相同。排除时间的四字节后，两份 Usbload.bin 仍有 139 个字节不同。写入器在 0x00641C39 至 0x00641C49 整体复制 1,704 字节，已知语义字段仅占其中一部分。当前证据支持在上述范围重建有效字段，无法据这六个相同输入确定唯一的全文件结果。补齐全文件仍需要其余字节对应的独立输入或与目标构建匹配的历史编译状态。

```powershell
py -3 tests/verify_usb_metadata_projection.py --git-revision e3b72657 --executable "build/amz070w01r/KinSealStudioLite.exe" --report "USB对照.json" "安装目录/compile/load.kns" "六页原厂工程.kns"
```
