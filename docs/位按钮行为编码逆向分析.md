# 位按钮行为编码逆向分析

日期：2026-11-15。范围：原厂 V5.1 离线模拟器、安装包 AMT070W124-L800X480R 固件，以及已有编译差分和阶段10人工观察。此次静态分析不代表新增实屏测试。

本轮已从编译字段推进到原厂 PC 模拟器和安装包 ARM 固件的行为消费者：四操作、条件掩码、容差比较、通知、宏请求、按压计数及部分取消链均有机器码依据。ARM 与 PC 的权限、通知、按压实现确有差异。核心行为已明显清楚，但屏内固件身份、全部取消事件、真实时基、异常值和 PLC 完成次序尚未闭合，不能宣称100%恢复。

位按钮记录主要编码操作枚举、地址、条件、时间、通知参数和宏索引；预置固件函数据此处理事件。普通SET/RESET/JOG/TOGGLE不是每个按钮另下载一段动作机器码；启用宏时，按钮记录引用另行编译的宏。理解这两层后，才能区分“字段已编码”“固件规则已恢复”和“当前设备已实测”。

## 2. PC 模拟器：从设备记录到运行对象

`0x4542E0` 按 `源基址 + 输入索引×0x280` 取记录。type10分支在 `0x454327` 设置 `ECX=0x70`，随后 `REP MOVSD` 将112个32位字，即448B，复制到：

```text
runtime_base = 0x14D22C60 + (输入索引 + 参数偏移) × 0x624
source_record[0..0x1BF] → runtime_base[0..0x1BF]
```

这是复制瞬间的映射。设备槽长640B，模拟器对象步长1572B，两者不是同一个结构尺寸；此处没有复制剩余192B。随后 subtype0 将 `runtime+0x11D` 清零；`+0x100` 非零时改写 `+0x104`；地址槽中还会存放运行值缓存。因此不能把运行内存重新原样写回编译文件。

它登记的地址指针包含 `+0x4C` 触控位地址、`+0x70` 通知、`+0x94` 显现位地址、`+0x198` 监视和 subtype0 的 `+0x118` 操作地址。当前这条装载路径没有因此证明现代字条件地址、全部地址转换及上游输入文件完全相同。

地址槽本地编码：+0路由0，+1为`B=0x42`或`W=0x57`，+8为LE32地址；+2有原厂来源元数据，不能任意归零解释；操作交替时源槽+5为1，但该模拟器装载后将操作槽+5清零。运行槽+0xC及+0x1C还存double当前值和变化检测辅助缓存；操作会将辅助缓存强制写为反值，不能统称真实历史采样，也不能当成静态配置常量。

权限完整文件编码仍沿用协议§14.2：位/字/等级掩码`4/2/1`，五类型`4/5/2/3/8`，六比较`<、>、==、<>、<=、>=`对应0..5；比较值/容差均LE f64。触控比较值/容差为`0x24/0x2C`，显现为`0x34/0x3C`；触控字地址`0xB8`、显现字地址`0xDC`。这些存储事实不自动证明消费公式。

## 4. 四操作的执行规则与先后关系

在已见入口中，先检查运行显现标志非0，再调用触控权限函数；返回值为1才进入 `0x40F3B0`。操作处理函数如下：

| 枚举 | 函数 | 已见行为 |
|---:|---|---|
| 0 | `0x410600` | 主写入值1；调用地址helper；可选通知；更新同址监视缓存 |
| 1 | `0x4106B0` | 主写入值0；其余顺序相同 |
| 2 | `0x410760` | 主写入值1，并将主地址登记到释放队列；通知地址不登记该队列 |
| 3 | `0x410820` | 主地址缓存double恰为1时写0，否则写1；更新缓存及可选同址监视 |

`0x40F3B0`在操作helper返回后尾调用`0x431490`登记宏请求；随后上游`0x40E510`调用`0x410920`，仅向匹配的type10目标复制源操作缓存：目标须为subtype0且监视模式非0，或subtype4且模式为1，再比较route/family/node/address四元组。SET/RESET仅在自身`+0x181==1`且`+0x184!=0`时更新源操作缓存，故这次复制不保证所有监视配置都立即显示正确新值。所见正常链的程序顺序为：

```text
显现判定 → 触控判定 → 主写helper → 可选通知helper
→ 满足条件的同址缓存更新 → 宏请求登记 → 限定目标的缓存复制
```

`0x4103C0` route0调用`0x438830`，B地址直接写本地字节数组的`value & 1`；W按1/2字存入本地字数组。route1/2写入两套队列，入队上限判断为200。调用处没有主写成功返回值检查，也没有看到事务回滚。因此上述顺序不能提升为“PLC确认写入成功后才通知/运行宏”，更不能把Lite事务策略认作原厂行为。

`0x431490`只在宏使能为1、全局就绪值为1且有符号字节宏索引小于宏计数时，将对应状态写2并置调度标志。它不在本函数内解释宏字节码；负索引防御也未由这条比较证明。编译器目前限制索引0..99，不能因反编译分支宽松就扩大有效输入范围。

## 5. 点动松开：已恢复独立释放队列

`0x410760`对主地址调用helper时令`EDI=1`；通知调用前清`EDI=0`。`0x4103C0`将需要释放的主地址、路由、控件索引记录到12B条目队列，上限200。

`0x40E480`在某全局模式标志为0时先调用`0x410C00`，再按控件子类处理释放。`0x410C00`遍历已登记条目，尝试向主地址写0或入队0；仅在源`+0x181==1`且监视模式非0时同步同址缓存并调用上述限定目标复制，之后清队列计数和活动标志。外部队列已满200时跳过入队，随后仍清释放队列，不能声明必定清零成功。此函数没有重新调用触控权限判定，也没有重新发送通知或登记宏。不能据此保证所有移出、隐藏、切页和失捕获路径都会调用它。

`0x44BBA0`的消息类型`0x26`中，通知码1/4走`0x40E730`，通知码2走`0x40E480`；这些数值尚未全部绑定到窗口库的事件命名及全部主窗口入口。另一路全局模式为1时，`0x40E330`对点动登记延后释放，由`0x43EF10`等调度后调用释放helper。延迟和真实PLC生效时刻未测。

`0x410C00`还有“调用计数超过100后再写0”的路径，调用`0x4109B0`并记录`ReWrite_diandong`。100是调用计数，不能写成100毫秒。该helper只读取释放队列首条，先将计数置1，仅route1/2再入队0，route0不在此再次本地写；所见helper本身没有重复检查外部队列小于200，不能描述为全部点动地址的可靠重试。拥塞后果和跨页生命周期仍需补证。

## 6. 权限与显现：确认了模拟器的兼容性限制

`0x44DAC0`以`ECX=runtime_base+0x14`调用`0x44DA20`。后者读取`runtime+0x21`，按精确值比较，而不是逐位测试现代掩码：

| 值 | 该函数行为 |
|---:|---|
| 0 | 位目标0而缓存值1，或位目标1而缓存值0时返回2；其它返回1 |
| 1 | 当前等级−1小于记录等级值时返回0；否则1 |
| 3 | 上述位拒绝条件或等级不足时返回3；否则1 |
| 其它，包括2/4/5/6/7 | 默认返回1 |

位缓存在`runtime+0x58`，来自触控位地址槽+0xC。这个函数没有读取字条件类型、比较枚举、比较常量、容差或字条件地址。位拒绝条件只比较double 0/1，不宜重写成任意值的`current != target`。

`0x40E510`仅返回1才操作；返回0另调用拒绝处理`0x44DD50`；2/3不操作。显现函数`0x44D990`同样按0/1/3解释`runtime+0x22`，使用显现位缓存及等级，然后由`0x451E20`维护可见状态和绘制状态。

这证明“现代4/2/1文件字段原样进入所见函数”会与该模拟器解释不同。尚未排除上游输入转换或其它入口差异，不能因此断言实物固件忽略权限。ARM 条件组合与有限数容差公式的新增证据见第9节；本节仅描述该 PC 二进制，NaN及实屏边界仍未闭合。

## 7. 通知与宏：调用次序已见，完整语义仍开放

四操作的通知路径在`+0x16`非0时，从`+0x20`取一个位值，使用`+0x70`地址槽，将写入长度置1、值低字节设置后其它字节清0，再调用同一地址helper。所见路径没有按`+0x23`模式、`+0x19`类型、`f64@+0x44`常量分派字通知。

这条链只足以确认位值式通知的程序次序。原厂文件的字通知编码仍有已有差分证据；该模拟器当前所见消费者无法覆盖它。Lite“位/字通知同时开启则拒绝”是保护策略，不能反推原厂文件无双开表示；历史原厂双开样本保留位优先的限定事实。

点动释放队列只保存主地址，因此所见释放函数不重复主操作的通知和宏登记。宏调度开始、结束、重复点击合并、宏与通信队列并发的最终次序尚未完整追出。

## 8. 按压延时：字段明确，所见模拟器支路不可达

`0x40E521 MOV EAX,0x72`，`0x40E526 CMP EAX,0x75`，中间MOV/PUSH不改比较标志，`0x40E52F JL 0x40E55C`必成立。于是正常入口跳过`+0x1BD`使能判断、`+0x1BE`时间读取和计时登记。Ghidra不可达提示与汇编相符。

`0x72`的业务含义尚未证明，本文不把它命名为固件版本。不能修改它后把新行为归到原二进制。已知UI×100ms的编码、Lite溢出保护655上限，与原厂实际计时起点、触发时刻、抬手取消、重复触发是不同问题。

## 9. ARM 固件：已恢复的真实消费规则

以下地址仅针对第1节固定 SHA 的安装包固件。它是实际 ARM 程序，但尚未只读认证为当前屏内正在运行的那一版。本轮未执行、烧写或修改固件。

### 9.1 分析入口与可复现边界

REA 的当前 Windows Ghidra 接口拒绝 raw ARM 输入，因此使用本机已有 Ghidra 12.1.4 headless 和 Capstone 5.0.7 直接静态分析，设置、缓存和临时文件均放 Z 盘。没有安装 Linux 或改 REA 配置。首次 Ghidra 项目路径含点号目录而失败的日志保留；后续使用专属无点号项目路径成功。

固件含32B头，文件`+0x20`为 ARM 入口。静态映射为`VA=fileOffset+0x8001FFE0`，入口`0x80020000`；异常向量、跳转目的地、scatter表和解压后`ControlPara.dat`字符串指针交叉支持该映射。ARM/Thumb交互入口也已识别。初始化RW段解压长度`0x5574`，SHA256 `2880fba2e52e80abc614fc84926459f55f2e833557307ddd866294b602e4fcd0`。重建影像含合成零BSS，仅供静态寻址，不是可烧写文件。

保留 [memory-map.json](bitbutton-rea-evidence/firmware/memory-map.json)、原始汇编/反编译、定点原字、脚本与日志。Ghidra有函数边界及标志传递恢复失败；例如`0x8007F13C`伪代码扩大内联、浮点减法入口只识别4B。因此下述条件、跳表、加减公式以对应汇编和`raw-evidence.json`为准，首轮反编译失败不改写为成功。

### 9.2 运行对象、四操作和执行次序

运行基址`0x80146B34`，对象步长`0x5C8`（`0xB9×8`）。`0x8007F13C`读取子类`+0x106`，先调用按压处理`0x80054ED0`；后者返回1就立即退出本次分派。子类0随后检查可见缓存`+0x286`及触控权限，仅权限返回1执行操作。

| 操作字段`+0x114`低字节 | ARM 处理函数 | 已确认的行为 |
|---:|---|---|
| 0 | `0x8002B038` | 主地址写1，随后通知、条件性缓存更新 |
| 1 | `0x8002AF44` | 主地址写0，随后通知、条件性缓存更新 |
| 2 | `0x8002AE44` | 主地址写1，并登记到释放队列；通知不登记释放 |
| 3 | `0x8002AD18` | 按主地址double缓存是否等于1决定写0或1 |

设备编码仍为LE32操作枚举；该消费入口实际只读低字节，不能据此放宽编译器合法值。其它低字节没有四操作调用，却仍可能走到后面的宏请求，畸形输入不纳入有效规则。

`0x8007C1E4`接收对象索引、是否登记释放及地址槽；route0走本地写`0x8007BDB0`，route1/2走外部队列，并检查对应队列计数小于200。主写helper前还有共享写缓冲整理`0x8007C0DC`，不能把每次写都理解成独立同步事务。正常有效操作的调用关系为：

```mermaid
flowchart LR
  A[按压登记或再次进入] --> B[可见缓存及触控条件]
  B --> C[主地址写入或入队]
  C --> D[可选位或字通知]
  D --> E[条件性缓存更新]
  E --> F[宏请求登记]
  F --> G[匹配控件缓存传播]
```

同址缓存传播为`0x80040820`，不是所有同地址对象无条件同步。外部主写、通知、宏请求间没有在这条链上等待PLC完成确认；程序调用顺序不能写成设备执行成功顺序。

### 9.3 触控与显现条件：掩码、组合和容差

触控wrapper把`record+0x14`交给`0x80057258`。使能0直接返回1；否则依次测试`+0x21`的位条件4、字条件2、等级条件1。全部启用条件须通过，**是AND组合**。位或字拒绝使返回值为2，随后其它条件通过不会把它改回1；等级不足最后覆盖成0，因此等级拒绝的处理优先。

| 条件 | 消费规则 |
|---|---|
| 位 | 目标0且缓存恰为1，或目标1且缓存恰为0则拒绝；不能扩为任意double不相等均拒绝 |
| 字 | 使用字地址的double运行缓存、比较枚举、f64目标与容差；读取宽度/类型如何转缓存需另查地址读取链 |
| 等级 | `currentLevel - 1 >= storedMinimum` 才通过；编译记录已保存UI最低等级减1 |

令当前字缓存为`x`、目标为`v`、容差为`t`。触控函数在字条件启用时将负容差在运行对象内钳为0。对有限正常数且算术结果正常的输入，六个比较编码的允许条件如下：

| 编码 | UI比较 | 允许条件 |
|---:|---|---|
| 0 | 小于 | `x < v` |
| 1 | 大于 | `x > v` |
| 2 | 等于 | `v - t <= x <= v + t`，两端包含 |
| 3 | 不等于 | `x < v - t` 或 `x > v + t`，严格区间外 |
| 4 | 小于等于 | `x <= v` |
| 5 | 大于等于 | `x >= v` |

只有等于/不等于使用容差区间；不把容差套到其余四个比较。跳表、浮点加减helper和条件分支共同支持公式，不能直接抄反编译器的布尔临时量。NaN、无穷、次正规数和溢出尚未形成完整真值表。比较序号≥6跳过字拒绝分支，不能声称固件会拒绝非法枚举。

显现函数`0x80057074`同样使用4/2/1的AND组合和对应六比较。总使能`+0x15`、掩码`+0x22`、位目标`+0x1E`、位缓存`+0xA0`、字比较`+0x1B`、目标/容差`+0x34/+0x3C`、字缓存`+0xE8`、等级`+0x1F`。但其位、字、等级拒绝全部返回0，允许返回1，不使用触控的0/1/2拒绝分类。触控字缓存为`+0xC4`，二者均是运行地址槽相对+0xC的double，不是编译时常量。

### 9.4 通知与宏：模式优先级、数值类型与异步边界

`0x80060E5C`检查`+0x16`总使能。若`mode@+0x23 & 1`则用`+0x20`位值；否则`mode & 2`才取`f64@+0x44`字值。因此双开时**位通知优先**，不是同时发两次。通知共用地址槽`+0x70`，写长度存其相对`+3`。

| 字类型`+0x19` | 写长度（16位字） | 转换分支 |
|---:|---:|---|
| 2 | 1 | 有符号整数转换helper |
| 3 | 2 | 有符号整数转换helper |
| 4 | 1 | 无符号整数转换helper |
| 5 | 2 | 无符号整数转换helper |
| 8 | 2 | double到float转换helper |

这是五个合法类型的分派和宽度；极端数值的舍入、溢出、NaN和传输字序不能由函数名或宽度推定。类型6/7的跳表直接落最终写helper，不是明确拒绝；编译器应继续限制合法类型。Lite设备编译器当前拒绝位/字通知双开，是该入口的现有保护策略；PC离线入口的差异另见§9.7。本轮没有改产品逻辑或放开该限制。

四操作helper返回后，上层调用`0x80074830`：宏使能等于1、全局就绪等于1、**无符号byte索引小于宏计数**才写对应状态2并置调度标志。与PC所见有符号索引不同。这里是登记宏请求；宏开始/结束、忙时重复请求、通信与宏并发及失败回滚仍未完整恢复。

### 9.5 按压计时：已找到登记、计数、再入和部分取消

`0x80054ED0`使用一组全局状态：对象索引byte在`0x80100270`、活动标志在`0x80100271`、计数u16在`0x80100272`、阈值u16在`0x80100276`。使能必须等于1；活动标志为0时登记当前索引、清计数、保存`+0x1BE`低16位阈值并置活动，返回1使上层暂不操作。活动为1时清活动并返回0，允许上层继续；这里没有核对原索引，不能解释为每控件独立计时器，也不能单凭此断言事件层允许绕过延时。

任务`0x80082248`在活动时计算`(threshold * 0xCCCD) >> 20`，对全部65536个u16输入已做纯数学核对，等价`floor(threshold/20)`。计数**相等**才尝试查找已登记控件、检查其状态，再以`0x8008A100`发送消息`0x26`、参数1；之后递增u16计数。末尾根据状态向延时函数传20或100。尚未证明OS tick配置及墙钟时基，所以不把“UI×100的字段”直接升格为精确毫秒触发承诺。

`0x80056840`清索引、活动、计数、阈值及另一状态。已见初始化调用、窗口消息`0x26`的子码2/3分支调用它。窗口库事件命名、移出/隐藏/切页/失捕获是否全部到达取消、触发与松手竞争、长按重复和u16回绕仍需补证。事件只到发送请求不等于已完成按钮动作。

### 9.6 点动释放：实际清零消费者和拥塞边界

`0x8003A670`仅在释放列表`0x801882C0+9`为1时处理已登记条目。route0调用本地写`0x8007BDB0`，数据参数为0：LB（类型`0x42`）存0，字内位（类型`0x5F`）清相应bit；route1/2向外部队列加入double 0，仍受容量200限制。处理后清活动标志和释放计数；若外部队列已满，本次没有入队也会清记录，不能保证异常通信下实际清零。

`0x8007F490`在配置`[0x80212E68+0xF8B]==0`时直接调用该消费者；另一模式中，`0x8007F50C`在点动释放分支置`0x80100285=1`，再由`0x8005FD28→0x800606E8`在传输扫描位置达到计数时触发释放处理。此配置的UI名称未确定；两条路径不能统一成固定时间延迟。

已见清零消费者没有调用通知`0x80060E5C`或宏请求`0x80074830`，也未重新走触控条件；因此这条释放链不会再次发送通知/宏。外层哪些事件必达释放、切页和隐藏竞争、外部队列满后的补偿及PLC最终值仍待核。

### 9.7 与当前 Lite 实现对照：已定位的具体差异

本轮只读对照当前源码，未更改产品行为。以下区分PC离线模拟入口和设备编译入口，避免把两条路径混为一谈。

| 当前源码路径 | 现状 | 与本轮 ARM 规则的关系/后续动作 |
|---|---|---|
| `src/simulation_runtime.cpp` 条件校验 | 拒绝零子条件、多条件、非零容差 | ARM无子条件允许、支持AND和容差区间；后续扩离线范围需采用本轮公式并保留未验证异常边界 |
| 同文件按压校验 | 启用按压计时仍拒绝 | ARM有全局门控与任务计数；先核真实时基和全部事件，不能直接假设精确UI毫秒 |
| 同文件位/字通知 | 两个独立if；属性校验允许双开 | PC离线入口可达双写，与ARM位优先不同；这是明确待修差异 |
| `src/native_bit_button_control.cpp` 设备通知编码 | 位/字双开仍明确拒绝 | 属编译器保护范围；本轮没有改成发送双写或放开限制 |
| `src/simulation_runtime.cpp` 操作事务/宏 | 先副本预检后提交；宏跳过 | 事务原子性和宏完成不能拿来代表原厂ARM规则 |
| 同文件及`src/simulation_window.cpp`取消事件 | 释放、移出、失焦等强制点动清零 | 是当前Lite规则；原厂所有对应事件尚未闭合，不能宣布完全等价 |

这些差异并不否定已有基础四操作实屏结果，也不表示编码器没有实现整个位按钮。统一待修/待验仍挂C02运行问题，并明确入口、版本和下一最小探针。
