# AMZ070W01 Bootloader、应用启动与下载边界

日期：2026-11-22（Asia/Shanghai）。对象为原厂 V5.1 随附 AMZ070W01.bin、原厂 PC 可执行文件及本目录的反汇编。只读静态分析；未执行原厂程序、未访问 USB、未烧写设备。用户本轮确认：目前只有现有文件，没有原厂量产包、独立启动文件或整片 NAND 备份。

## 1. 当前能回答到什么程度

**已经确定：普通工程下载与“强制底层更新”由运行中的 HMI 固件接收；强制底层更新写的是应用固件区，从 NAND 主数据区偏移 0x100000 开始。所追踪的正常更新路径不擦写前 1 MiB。**

**尚未确定：冷启动 Bootloader 的原始字节、精确 Flash 起止位置、复位 ROM 入口，以及它如何把应用镜像装入 RAM。不能将“前 1 MiB 未被这条更新路径覆盖”推成“Bootloader 就占满前 1 MiB”。**

| 问题 | 本轮结论 | 证据状态 |
|---|---|---|
| AMZ070W01.bin 是什么？ | 含 HMI、µC/OS-II、驱动、更新接收器和自身 C 运行时启动的应用镜像。已证入口要求 RAM 预先可用。 | 已证指定入口链 |
| 当前上位机是否每次下载 Bootloader？ | 所追踪的普通工程/强制更新链未另外发送独立 Bootloader；强制更新发送所选 fbottomFile。 | 已证所追踪 PC 分支与 AMZ 消费链 |
| 应用固件存在哪里？ | 从物理候选块 8、页 0x200、主区偏移 0x100000 开始；坏块会使实际占用向后延伸。 | 已证 |
| 0x80020000 是 Bootloader 的 Flash 地址吗？ | 不是 Flash 偏移；它是此应用正文的预期 CPU 运行地址。 | 已证 |
| 真正的冷启动 Bootloader 存在哪里？ | 未取得其镜像；前部保留空间是后续调查候选，精确位置未知。芯片固化 BootROM 与外部加载器也必须分开。 | 未闭合 |
| 一块正常出厂的屏是否需要重下 Bootloader 才能换 UI？ | 在既有固件正常运行、已支持的工程下载路径下不需要。 | 由接收器所在镜像及写区范围推导 |
| 空白 NAND/新板能否只靠 UI 或这个 BIN 启动？ | 现有文件和常规下载路径没有提供完整冷启动部署方案；不能承诺能启动。需要匹配的启动材料、板级初始化及生产烧录方法。 | 材料缺失，不能作已验证结论 |

## 2. 不同地址不能混用

| 地址体系 | 已证数值 | 含义 |
|---|---|---|
| PC 文件偏移 | 0x00..0x1F | 32 字节 eGON.EXE 头，包含入口分支 |
| PC 文件偏移 | 0x20 | 应用正文首条指令 |
| CPU 运行地址 | 0x80020000 | 应用正文起点；不是 NAND 偏移 |
| 分析清单坐标 | 0x8001FFE0 | 为使正文对应正确地址而给文件头安排的坐标；不证明冷启动加载器把完整头实际放在这里 |
| NAND 物理候选块号 | 8 | 写入 helper 的起始块；不是“第 8 个好块” |
| NAND 主区偏移 | 0x100000 | 8 × 128 KiB；不包含 OOB 字节 |
| NAND 主区区间 | [0x100000, 0x200000) | 当前镜像完整接收、无坏块时 USB 写请求的范围 |
| NAND 主区区间 | [0, 0x100000) | 该正常更新路径没有擦写的前部区域；内部内容/分区尚未恢复 |

原有总报告将工程存储编号统称“逻辑块”。本轮对升级写 helper 的进一步核对表明：**0x8002B818 的起点先作为物理候选块使用，坏块顺序跳过；不能把这一具体写路径解释为先查 FTL，再写第 N 个好块。**其它读取/资源路径应逐条分析，不由此一并改名。

## 3. 已恢复的启动链

```text
上电复位
  └─ 最早期启动入口、BootROM/外部加载器、DRAM 冷初始化：本样本未恢复
       └─ 将应用从存储装入可执行 RAM：执行者、复制头的策略未恢复
            └─ 应用正文 0x80020000                         已证
                 ├─ 设置各 ARM 模式栈及异常向量
                 ├─ scatter 复制、解压、清零
                 └─ 0x800201E8 → 0x800AB67C
                      ├─ 0x800B4F2C 板级/应用初始化
                      ├─ 0x8003BF78
                      └─ 0x800B55CC → 任务创建 → HMI 调度
```

这里前三段没有冒充已恢复的原厂调用链。要完整解释 Bootloader，仍须取得最早期启动材料。

具体证据：

1. [汇编第 9 行](full_disassembly.asm#L9)：文件 0 为 ARM 分支，跳过 32 字节头。文件头含 eGON.EXE、EXEC，长度 0xF6E00 与文件一致。
2. [汇编第 21 行](full_disassembly.asm#L21)：正文设置 UND/ABT/IRQ/FIQ/SYS/SVC 栈，栈值落在 0x81FB5000..0x82000000。异常向量目标由 CP15 bit13 读回值选择 0 或 0xFFFF0000；后者不能直接认作本轮已证 BootROM 地址。
3. [汇编第 59 行](full_disassembly.asm#L59)：scatter 在应用初始化前即写 RAM。三项表使压缩输入暂存到 0x80158D68，解压到 [0x8011383C,0x80158D68)，清零 [0x80158D68,0x8038541C)。因此已证入口要求相应内存预先可用。
4. [汇编第 191 行](full_disassembly.asm#L191)：运行时交接经 BX r12 到 0x800AB67C；[应用入口](decompiled_pseudocode.c#L137573)连接三段初始化。MMU/cache 配置 0x800B4CEC 已在 scatter 之后，不是前面的 RAM 冷初始化。
5. [汇编第 156242 行](full_disassembly.asm#L156242)：创建 0x80087CF0 任务，随后交给调度。

已排除两个字符串误判：[SDRAM Init 分支](full_disassembly.asm#L137507)只打印并返回，没有实际 DRAM 控制器初始化；[Booting... 函数](full_disassembly.asm#L150320)是绘图，不是上电加载器。第二个 eGON.EXE（file 0x39068）是镜像校验常量，也不是第二份启动镜像。

## 4. 强制底层更新实际上怎样写入

PC 原厂 EXE 的 0x9F1C54 从安装目录 Firmware/ 加线程 +0xE4 文件名读取完整文件；该字段来自型号配置 fbottomFile。AMZ 对应 AMZ070W01.bin。原厂发送命令 0x69，命令帧 +0x15 写小端长度、+0x19 写逐字节累加和，然后发送完整文件，最后以 0x35 结束。此 helper 没有另读 boot0/boot1 或独立 Bootloader 文件。

AMZ 的接收和写入链如下：

| 步骤 | 原厂行为 | 定位 |
|---|---|---|
| 0x69 | 置升级状态，登记声明长度/累加和；在 buffer−0x20 另存长度/校验和 | [ASM 80920](full_disassembly.asm#L80920)，0x8006CB78 |
| 数据接收 | 复制到 buffer + receivedCount，再推进计数；不跳过镜像头 | [ASM 62950](full_disassembly.asm#L62950)，0x8005B844 |
| 0x35 校验 | 按声明长度逐字节加和；检查 buffer+4 的 eGON.EXE；另有兼容标志和 image[0x1F] 条件 | [ASM 80902](full_disassembly.asm#L80902)、[ASM 80966](full_disassembly.asm#L80966) |
| 写长度 | `((receivedCount >> 17) + 1) << 17`，整块长度也会再加一块 | 0x8006CCC4、0x8006CD10 |
| 起点/源 | `0x8002B818(8, buffer, writeLength)`；完整头仍在源缓冲开头 | [ASM 80986](full_disassembly.asm#L80986) |
| 擦块/写页 | 以当前物理候选块乘每块页数得到 row；D8 擦块，10 Program Execute 写页 | [ASM 13220](full_disassembly.asm#L13220)、[ASM 148657](full_disassembly.asm#L148657)、[ASM 148968](full_disassembly.asm#L148968) |

RW 初始化数据中的表位于 0x80157D14（RW 文件偏移 0x444D8）。11 个非零项、每项 20 字节，项内 +8 页大小均为 0x800、+16 块大小均为 0x20000；未知 ID 回退第 0 项也相同。由此每块 64 页，块 8 的首 row=0x200，主区偏移为 0x100000。

写 wrapper 0x800AE33C 保留原 row 并传给 0x800AE3EC。反向映射只用于首 page 的 OOB 标签，不改变传给 Program Execute 的 row。坏块向后跳过时不消耗源数据；因此正常合法长度、没有整数回绕的路径不触碰块 0..7。实际物理末端受坏块影响。

当前文件长 0xF6E00=1,011,200 B，完整接收后 USB 请求写 0x100000=1,048,576 B。多出的 0x9200=37,376 B 来自接收缓冲后续区域，**没有证明被填 0 或 FF**。不能据主机文件直接声称这段 NAND 尾部的确定内容。

### 成功判断的限制

- USB 0x35 路径没有读回比较；独立的介质升级 [0x8008F528](decompiled_pseudocode.c#L106511)才有块 8 写入、读回、memcmp，以及比较失败后最多再写一次。
- 擦/写等待 helper [0x800BAED8](full_disassembly.asm#L161759)只等待状态 bit0 清零；所看擦/写函数没有检查 erase/program fail 位即返回 1。
- “update ok”只是传给 0x800B4F24 的字符串，该例程本样本为 BX LR。兼容/签名条件拒写也能进入此收尾，不能把该字符串当作设备实际日志或成功烧写证据。
- 以上是静态恢复，不是本轮执行了固件升级。没有由此验证故障恢复、畸形长度或断电安全性。

## 5. 为什么不能直接说 Bootloader 在哪里

有三种对象必须区分：芯片固化的最早期启动代码、可能位于外部存储的装载器、应用镜像内部的启动汇编。当前文件直接提供了第三种和应用更新接收器，没有提供完整的前两种实现。

“应用写在 1 MiB 起”“应用正文在 RAM 的 0x80020000 执行”能建立更新边界，但缺少中间装载器，就不能恢复其 Flash 偏移、长度、冗余副本、校验方法或故障进入条件。即使平台家族高置信为全志 suniv，也不能把通用 boot0 布局当作这块原厂板的实测布局。

对安装目录的有界检查：Firmware/**/*.bin 87 份，根目录 EXE/DLL 22 份，TurboWriter 的 3 个指定 BIN，共 112 份、135,235,743 B。全文件明文 eGON.BT0/BT1/BT2/FES 零命中；84 份机型固件前 64 字节内在偏移 4 命中 eGON.EXE。此检查不排除无签名、压缩或封装的启动代码。

TurboWriter 随附 musb.bin、FA93_musb.bin 等；其 ChangeLog 指向 W55FA91/93/95 平台，不能拿来作为 AMZ 的启动文件。REA 的 DownT.dll/AMZUsb.dll PE 资源目录调查也未给出 AMZ 启动镜像；资源表检查不能排除任意非资源段或编码数据。

## 6. 能否用上位机取得 Bootloader 或给空片下载

所查维护分派中没有找到已证的任意 NAND 起点读出接口：

- 0x4F 经 0x80081068 → 0x8006CA28 → 0x80070244，固定读块 0x13（主区 0x260000）的工程快照；0x50 续传既有 RAM 缓冲。
- 上载初始化还可能先把运行数据保存到块 0x395/0x397、0x389、0x3C4。因此“工程上载”不能当作无副作用的全片备份。
- 内部固定低 page 读取涉及 NAND feature B0.bit6 切换，只归并少量字节为内部结果，没有已证整页上传路径。

定位：[维护分派](full_disassembly.asm#L33005)、[上载初始化](full_disassembly.asm#L80797)、[固定工程块读取](full_disassembly.asm#L84408)、[续传](full_disassembly.asm#L102093)。检查范围不包括尚未取得的 BootROM/启动阶段协议；未排除另有生产或恢复工具。

实际使用应分情况：

1. **现有正常屏更新 UI**：使用已验证的工程下载即可，不需要另找 Bootloader 重刷。
2. **现有正常屏更新 HMI 底层**：原厂强制更新传输机型 BIN，由运行固件写应用区；这是应用固件升级，不是已证的启动区重建。
3. **空白 NAND、新板或启动区损坏**：现有材料不足以做可重复部署。需要匹配板型的启动镜像/整片备份及生产烧录或 ROM 恢复协议。究竟由哪款上位机、编程器或调试接口完成，当前不能指定。
